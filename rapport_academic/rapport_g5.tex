\section{Introduction et Contexte du Projet}
Le Gouvernement du Cameroun, dans le cadre de sa stratégie nationale de développement de l'économie numérique, a initié le déploiement de Centres de Développement du Numérique Universitaire (CDNU) au sein des institutions d'enseignement supérieur. Ce projet national vise à interconnecter ces 11 centres régionaux à travers une infrastructure de cloud computing souveraine, résiliente et sécurisée hébergée sur Amazon Web Services (AWS).

Dans ce contexte, le Groupe 5 s'est vu confier la responsabilité du Lot "Services Managés". Ce lot constitue les fondations persistantes et logicielles de la plateforme nationale, englobant les systèmes de stockage d'objets, la gestion centralisée des données relationnelles, ainsi que l'hébergement sécurisé des conteneurs applicatifs.

\section{Architecture Technique et Spécifications IaC}
Le lot orchestré par le Groupe 5 est conçu en utilisant l'Infrastructure as Code (IaC) avec le logiciel Terraform. Les ressources sont déclarées dans des modules réutilisables, paramétrables et indépendants.

\subsection{Base de Données Relationnelle RDS PostgreSQL}
Le coeur des données de l'application nationale repose sur une instance Amazon RDS PostgreSQL. Les choix d'implémentation sont présentés ci-dessous :
\begin{itemize}
    \item \textbf{Moteur et Version} : PostgreSQL version 15.18. Ce choix garantit la pérennité de l'infrastructure et supporte les mécanismes de sécurité requis.
    \item \textbf{Dimensionnement} : Instance de type \texttt{db.t3.micro} avec un volume de stockage de 20 Go de type GP3, offrant 3000 IOPS de base.
    \item \textbf{Chiffrement} : La base de données est intégralement chiffrée au repos via une clé KMS dédiée.
    \item \textbf{Sécurité Réseau} : L'instance est déployée dans un Subnet Group privé et protégée par un groupe de sécurité n'autorisant les flux SQL entrant sur le port 5432 que depuis les sous-réseaux internes gérés par le Groupe 4.
\end{itemize}

\subsection{Stockage d'Objets Amazon S3}
Pour répondre aux besoins de stockage de documents de chaque université, le Groupe 5 déploie 11 paires de buckets S3 (22 buckets au total) avec une stratégie stricte de restriction publique et de cycle de vie.
\begin{itemize}
    \item \textbf{Bucket de données} : Stockage principal des fichiers administratifs et pédagogiques.
    \item \textbf{Bucket de logs} : Centralisation des traces d'accès réseau pour chaque requête S3.
    \item \textbf{Sécurité en transit} : Une Bucket Policy force l'utilisation exclusive d'HTTPS (TLS 1.2+) sous peine de rejet de la requête.
\end{itemize}

\subsection{Registre de Conteneurs Amazon ECR}
Le registre privé ECR accueille les images Docker de l'API développées par les autres groupes de travail.
\begin{itemize}
    \item \textbf{Scan de Vulnérabilités} : L'analyse statique des vulnérabilités CVE est activée au push de chaque image.
    \item \textbf{Politique de Nettoyage} : Conservation des 10 dernières versions tagguées (\texttt{v*}) et suppression automatique des images untagged après 7 jours.
\end{itemize}

\section{Intégration Systémique Inter-Groupes}
L'architecture globale étant collaborative, les ressources déployées par le Groupe 5 sont reliées aux autres lots de la façon suivante :
\begin{itemize}
    \item \textbf{Groupe 4 (Réseau)} : Intégration de l'instance RDS PostgreSQL dans les sous-réseaux privés et routages inter-CDNU.
    \item \textbf{Groupe 6 (API / ECS)} : Utilisation du registre ECR pour pousser les images de conteneurs de l'application et utilisation des Secrets de Secrets Manager pour la connexion à la base RDS.
    \item \textbf{Groupe 7 (Sécurité)} : Utilisation des ARNs des buckets S3 pour restreindre les permissions des rôles d'instances EC2 régionales.
    \item \textbf{Groupe 8 (Monitoring)} : Agrégation des alarmes de seuil CloudWatch (CPU BDD, espace de stockage restant) vers les serveurs de supervision centraux.
\end{itemize}

\section{Manuel d'Exploitation et de Déploiement}

\subsection{Initialisation et Planification Autonome}
Pour valider l'indépendance de nos modules, le déploiement a été modélisé de manière autonome via un VPC par défaut.
Les commandes d'initialisation et de test sont les suivantes :

\begin{lstlisting}
# Configuration des variables d'environnement (Clés AWS exclues de Git)
export AWS_ACCESS_KEY_ID="VOTRE_ACCESS_KEY_ID"
export AWS_SECRET_ACCESS_KEY="VOTRE_SECRET_ACCESS_KEY"
export AWS_DEFAULT_REGION="eu-central-1"

# Initialisation de Terraform avec reconfiguration du backend S3
../bin/terraform init -reconfigure

# Planification et validation à blanc
../bin/terraform plan
\end{lstlisting}

\subsection{Déploiement et Nettoyage}
Pour créer puis détruire l'ensemble des ressources de test, utilisez les commandes de cycle de vie Terraform :

\begin{lstlisting}
# Lancement du déploiement réel sur AWS
../bin/terraform apply -auto-approve

# Destruction et nettoyage complet des ressources après soutenance
../bin/terraform destroy -auto-approve
\end{lstlisting}

\section{Sécurité et Exclusion des Secrets}
Le Groupe 5 applique une politique rigoureuse de non-exposition des secrets d'infrastructure :
\begin{itemize}
    \item \textbf{Fichier .gitignore} : Configuré pour bloquer le téléversement vers le dépôt public GitHub des fichiers locaux contenant des clés d'accès AWS (\texttt{cdnu-admin\_accessKeys.csv}), de la configuration locale du backend (\texttt{.terraform/}), des états de ressources sensibles (\texttt{*.tfstate}), et du fichier de configuration du mot de passe de base de données (\texttt{terraform.tfvars}).
    \item \textbf{Intégration Secrets Manager} : Le mot de passe SQL d'administration généré de manière aléatoire et robuste par Terraform n'est stocké nulle part en clair dans le code, mais poussé directement dans AWS Secrets Manager.
\end{itemize}
